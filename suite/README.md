# Наскрізний набір задач

Набір малих різнотипних лабораторних для вимірювання головної метрики проєкту: яка частка задач проходить кожен етап від плану до захисту. Визначення рівнів готовності — в [документі мети](../docs/GOAL_AND_ACCEPTANCE.md).

Усі умови, вхідні файли й оракули написано для цього набору; чужих навчальних матеріалів тут немає.

## Склад

| ID | Тип | Мова | Вхід | Що перевіряє оракул |
|---|---|---|---|---|
| `s1-grades` | обробка даних, графік | Python | бриф + CSV | статистики груп перераховано незалежно |
| `s2-primes` | алгоритм | C | «сирий» текст студента | кількість і найбільше просте для кожного N |
| `s3-shop-sql` | бази даних | SQLite SQL | бриф + два CSV | результати чотирьох запитів |
| `s4-routing` | передача файла між кроками | Python | бриф + первинна умова | маршрути шести подій і файл перевірок |
| `s5-roots` | чисельні методи, варіант із таблиці методички | JavaScript | «сирий» текст + методичка DOCX | корінь, точність і кількість ітерацій для варіанта 3 |

## Етапи, які фіксує прохід

`created` → `planned` → `approved` → `executed` → `oracle` → `report` → `defense`. Задача проходить повністю, якщо досягла `defense`, оракул підтвердив результати, а звіт містить реквізити з глобальних налаштувань і ключові числа з результатів.

Для кожної задачі оракул також перевіряє навмисно зіпсовану копію результатів: вона мусить провалитися. Інакше оракул вважається недійсним і задача не зараховується.

## Запуск

Сервер і worker мають працювати (`scripts/start.ps1 -NoBrowser`), Docker — запущений.

```powershell
.venv/Scripts/python.exe scripts/suite.py run                 # усі задачі, ліміт $0.50
.venv/Scripts/python.exe scripts/suite.py run --only s2-primes
.venv/Scripts/python.exe scripts/suite.py check <results.json> # повторна перевірка оракулами без нових запусків
.venv/Scripts/python.exe scripts/suite.py selftest             # оракули на еталонних і зіпсованих даних
```

Результати пишуться в `data/verification/suite/<час>-<коміт>/results.json` (локально, поза git). Прохід на незакоміченій версії позначається `dirty` і для порівнянь не використовується.

## Правила

- Код, план, числа й статуси, згенеровані програмою, не редагуються. Оператор лише погоджує план без змін.
- Якщо план містить питання до користувача (`missing` чи `conflicts`), задача зупиняється на етапі `planned` з причиною `clarification`. Відповідати на питання автоматично набір не вміє.
- Оракул не передається моделі й не читає згенерований код, лише результати.
