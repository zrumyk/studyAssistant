Виконати локальну роботу «Маршрутизація мережевих подій» за первинною умовою routing-lab.txt, пункти 1–3. Варіант не задано. Мета — передати файл політики між двома окремими кроками та використати його фактичну структуру під час класифікації. Рішення має відтворюватися без мережі, зовнішніх служб і сторонніх пакетів.

Спочатку окремим кроком write створити один вихід routing-policy.json. Політика має містити пороги auth=4 і dns=2 та правила трьох маршрутів. Для відомої категорії severity >= порога дає alert, менше порога — archive. Для всіх невідомих категорій використовувати review незалежно від рівня. Формат ключів і представлення правил визначити в кроці write. Python-крок має врахувати фактичний вміст збереженого файла.

Окремий code-крок на Python stdlib отримує routing-policy.json як оголошений незмінний вхід. Прочитати його у програмі й використати в обчисленні. Політику повторно не створювати. Вхідні події: (a,auth,3), (b,auth,4), (c,dns,2), (d,dns,1), (e,other,5), (f,other,0). Порядок зберігається. Зберегти main.py, decisions.csv із колонками event_id,route і checks.json. Незалежні перевірки запускаються після програми та мають виконати assert для всіх шести подій, рівності порогу, невідомої категорії й порожнього входу. Перевірити, що зміна порога в окремій тестовій копії політики впливає на результат без зміни програми. Початковий routing-policy.json залишити незмінним. У checks.json зберегти факти виконаних перевірок. Числа звіту брати з результатів запуску.

Останній крок report читає routing-policy.json, decisions.csv і checks.json. Звіт DOCX/PDF має містити мету, вхідні дані, фактичну політику, реалізацію, таблицю маршрутів, граничні перевірки й висновок. Титул використовує чинні глобальні ПІБ, групу та заклад. У матеріалі захисту пояснити, як змінюється маршрут на порозі, навіщо незмінний вхід та що доводить тест зміни політики. Ручних дій або зовнішньої передачі файлів немає.
