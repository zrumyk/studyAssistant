# Правила для агентів StudyAssistant

Чинна редакція від 13.11.2026. Це єдиний документ з інструкціями. Попередня редакція з історією 22.10–13.11 лежить в [архіві](docs/history/2026-11-13/AGENTS.md); вона пояснює минуле й не є вказівкою до дії. Пряма нова вказівка користувача має пріоритет над цим файлом.

## Що читати на початку сеансу

1. Цей файл.
2. [STATUS.md](STATUS.md) — поточний стан і точка продовження.
3. [WORK_PLAN.md](WORK_PLAN.md) — розділ «Активні задачі».

Решту читайте лише за потреби задачі: [мета й приймання](docs/GOAL_AND_ACCEPTANCE.md), [карта коду й доказів](docs/handoff/SYSTEM_AND_EVIDENCE.md), [запуск і відновлення](docs/handoff/05_OPERATIONS.md), [аналіз причин](docs/audits/root-cause-2026-11-13/ROOT_CAUSE_ANALYSIS.md).

## Мета

Універсальна локальна платформа для лабораторних із комп’ютерних наук: умова й матеріали → план → погодження → код і виконання → перевірка → звіт → захист. Чотири лабораторні жовтня — історичні приклади, а не ціль. Готовність вимірюється часткою задач наскрізного набору, що пройшли кожен етап, за рівнями М0–М3 з [документа мети](docs/GOAL_AND_ACCEPTANCE.md).

## Незмінні правила користувача

Ці правила змінює лише користувач.

- **Бюджет.** DeepSeek до $5 на місяць і до $0,03 на запит. Модель — `deepseek-flash` без міркування; за рішенням користувача 13.11 вона достатня, порівняння моделей (SA-141) відкладено, сильнішу модель не пробувати без нового рішення. Один прохід наскрізного набору — до $0,50, але повний набір запускається лише після змін загальних механізмів; дрібні перевірки — офлайн на збережених відповідях. Обірвану відповідь моделі можна повторити один раз із більшим лімітом виводу; поточний код цього ще не вміє. Ключі з `.env` не читати у відповіді й не друкувати.
- **Чесність результатів.** Не редагувати згенерований лабораторний код, числа, звіти чи статуси в БД, щоб задача пройшла. Виправляється механізм програми, після чого задача запускається знову.
- **Справжні свідчення.** AutoCAD, Tinkercad, публікації, фізичні вимірювання підтверджує лише людина. Програма готує пакет і зупиняється.
- **Диск.** На D: завжди лишається щонайменше 10 GiB. Один важкий процес одночасно. Чужі образи, томи Docker і VHDX не видаляти.
- **Реквізити.** Титул, звіт і захист беруть ПІБ, групу й заклад із глобальних налаштувань. Кафедру й викладача не вигадувати.
- **Тести.** ЛМВ не тестувати. Новий тест має первинне джерело умови та бриф за [промптом](docs/TASK_BRIEF_PROMPT_UK.md). Виняток за рішенням від 13.11: дві з п’яти задач наскрізного набору запускаються на «сирому» вводі, без докладного брифу.
- **Погодження.** План конкретної роботи погоджується в застосунку до виконання. Для задач набору тестовий оператор погоджує план без редагування.
- **Самостійність.** За постійним дозволом від 06.11 агент сам виконує зміни, перевірки й запуски за планом у цих межах. Зупинитися й запитати треба перед зміною цих правил, моделі, мети, перед видаленням даних користувача та перед витратами понад $0,20 за день (рішення користувача 13.11; до того було $0,50).

## Як працювати

1. **Спершу виміряй.** Зміна загального механізму має підставу — задачу набору, яка зупиняється. Результат зміни оцінюється проходом набору до і після. Без такого проходу зміна не вважається перевіреною, навіть якщо модульні тести зелені.
2. **Ширина перед глибиною.** Працюй над етапом, на якому зупиняється найбільше задач набору. Не шліфуй етап далі, ніж потрібно, щоб задачі дійшли до наступного.
3. **Не зациклюйся на одному прикладі.** Якщо дві послідовні зміни механізму заради однієї задачі не покращили прохід набору, зупинись, запиши висновок і перейди до іншої задачі чи етапу.
4. **Жодних правил під конкретний випадок.** У ядрі промптів і в контролері немає назв бібліотек, наборів даних, архітектур, предметів, ID проєктів. Урок з однієї задачі потрапляє в загальний промпт лише в загальному формулюванні й після підтвердження на задачах двох різних типів.
5. **Спрощуй перед тим, як додавати.** Перш ніж створювати новий шлюз, поле схеми чи механізм ремонту, перевір, чи проблему знімає послаблення або видалення наявного. Новий механізм має вказувати, що він замінює.
6. **Модель не є суддею останньої інстанції.** Детермінована перевірка й зовнішній оракул мають пріоритет над вердиктом моделі в обидва боки. Нових модельних шлюзів, які зупиняють роботу, не додавати. Сумнівне зауваження моделі — це попередження користувачу, а не зупинка.
7. **Працюй в основному дереві.** Тестові проєкти створюй через API поруч із наявними. Ізольована копія потрібна лише тоді, коли експеримент може пошкодити дані користувача. Прототип, не перенесений у робочий шлях, не є результатом.
8. **Перевіряй код.** Після зміни — цільові тести, перед завершенням задачі — повний набір і Ruff. API та worker перезапускай лише за порожньої черги.
9. **Кажи як є.** «Завершено» означає, що критерій задачі виконано і є доказ. Розрізняй: реалізовано, пройшло тести, пройшло в реальному запуску. Про невиконане й неперевірене пиши прямо.

## Перед запуском

Перевір чергу завдань, вільне місце на D:, RAM і стан Docker. Знімок у документах не є живим станом. Оціни вартість запуску за збереженими квитанціями.

```powershell
Set-Location -LiteralPath D:\StudyAssistant
& .\scripts\start.ps1 -NoBrowser        # API 18573, worker 18574, Ollama 11434
$env:PYTHONPATH = "$PWD/backend"; .venv/Scripts/python.exe -m pytest
& .\scripts\stop.ps1
```

Робоча БД — `data/study.sqlite3`; для перегляду відкривай у режимі читання. Витрати: таблиця `cloud_requests`, плюс окремі копії аудитів 05–06.11 у `data/verification/system-audit-2026-11-05`.

## Документація

Повні правила — у [правилах документування](docs/worklog/README.md). Коротко:

- Кожен факт живе в одному місці: правила тут, стан у STATUS, задачі у WORK_PLAN, хід роботи в журналі дня.
- STATUS перезаписується й лишається коротким. Історія — в журналі.
- Після змістовного кроку: запис у `docs/worklog/РРРР-ММ-ДД.md` і оновлення картки задачі. Перед кінцем сеансу — оновити STATUS.
- Пиши повними реченнями українською. Не перелічуй те, що не змінилося.
- Робота з git описана в розділі «Git» нижче.
- Цей файл не доповнюється записами про стан.

## Git

Репозиторій — версії самої програми. Робочі нотатки розробки ведуться локально, поза git.

### Що в репозиторії, а що ні

- **У репозиторії:** `backend`, `frontend` (без `dist` і `node_modules`), `tests`, скрипти запуску, налаштування й перевірок у `scripts`, `README.md`, цей файл, документи про устрій програми в `docs/`, файли залежностей, `.env.example`, `.gitignore`.
- **Лише локально** (виключено в `.gitignore`): `STATUS.md`, `WORK_PLAN.md`, `HANDOFF.md`, `docs/worklog`, `docs/history`, `docs/handoff`, `docs/audits`, `docs/verification`, `docs/benchmarks`, історичні документи приймання, одноразові скрипти аудитів, а також `data`, `models`, `materials`, `tools`, `docker-data`, `.cache`, віртуальні середовища та `.env`.
- **Ніколи в репозиторії:** ПІБ, група, навчальний заклад та інші особисті дані користувача; ключі й токени; чужі навчальні матеріали (PDF курсів, архіви, набори даних); бази SQLite з робочими даними; файли понад 1 МБ без окремої причини.
- Новий документ про устрій програми клади в `docs/`. Нотатку про хід роботи, аудит чи доказ — у виключені папки. Документи репозиторію не посилаються на локальні нотатки: на GitHub ці посилання не відкриються.
- Після зміни `.gitignore` переконайся, що нічого локального не потрапило під відстеження: `git status --short` і `git ls-files` для змінених шляхів.

### Гілки

- `main` завжди в робочому стані: повний набір тестів і Ruff проходять на кожному коміті.
- **Прямо в `main`:** документація, дрібне виправлення в межах одного модуля з тестом, зміна скриптів, що не впливає на поведінку програми.
- **В окремій гілці:** зміни загальних механізмів — промптів, планування, рецензування, контролера (`engine.py`), схем, БД і міграцій, виконання й звіту. Назва: `sa-<номер>-<коротко>`, наприклад `sa-140-review-severity`.
- Гілку зливай у `main` після повного набору тестів, Ruff і, коли наскрізний набір уже є, після його проходу з записаним порівнянням «до і після». Злиття — `git merge --no-ff` локально. Після злиття гілку видали.
- Гілку, яка не покращила прохід набору, не зливай. Запиши висновок у журнал і видали її або залиш з поясненням у картці задачі.
- Гілки на GitHub не пушаться, якщо користувач не попросив.

### Перед комітом

1. `git status` і `git diff` — переглянь кожен змінений файл. `git add` роби за конкретними шляхами або після такого перегляду, а не наосліп.
2. Для змін коду: цільові тести, потім повний набір і Ruff. Якщо змінено `frontend` — `npm run build`.
3. Перевір відсутність особистих даних і ключів у тому, що комітиш. Особисті значення беруться з локальних налаштувань, тому самі в репозиторій не потрапляють:
   ```powershell
   $s = Get-Content data/settings.json -Raw -Encoding utf8 | ConvertFrom-Json
   $p = @($s.author, $s.group, $s.institution) | Where-Object { $_ } | ForEach-Object { [regex]::Escape($_) }
   git diff --cached | Select-String -Pattern (($p + 'DEEPSEEK_API_KEY=[A-Za-z0-9]', 'sk-[A-Za-z0-9]{20,}') -join '|')
   ```
   Порожній вивід — добре. Тестові заглушки ключів у `tests` допустимі. Не вписуй особисті значення в шаблони пошуку у файлах репозиторію.
4. Не комітити згенеровані дані, журнали запусків, кеші, результати лабораторних.

### Коміти

- Один коміт — одна логічна зміна. Не змішуй виправлення механізму з несуміжними правками документації.
- Повідомлення українською. Перший рядок до 72 символів, із номером задачі, якщо він є: `SA-140: рівні серйозності зауважень рецензента`. Далі порожній рядок і, за потреби, два-три речення: навіщо зміна і як її перевірено.
- Якщо середовище агента вимагає трейлер співавторства, додавай його останнім рядком.
- Коміт робиться після змістовного завершеного кроку, а не наприкінці сеансу одним великим комітом.
- Прохід наскрізного набору запускай на чистому робочому дереві й записуй у доказ ідентифікатор коміту (`git rev-parse --short HEAD`). Якщо дерево мало незакомічені зміни коду, позначай прохід як «незакомічена версія»; для порівнянь такий прохід не використовується.

### Пуш

- Пуш лише за прямою вказівкою користувача в поточній розмові. Дозвіл на один пуш не поширюється на наступні.
- Перед пушем: `git fetch`, переконайся, що `origin/main` не має комітів, яких немає локально (`git status -sb`). Якщо розійшлися — зупинись і повідом користувача, не зливай і не перезаписуй самостійно.
- Пушиться лише `main`, якщо користувач не сказав інакше. Теги — разом із пушем і лише ті, що описані нижче.

### Теги

Коли досягнуто рівня готовності (М0–М3), постав анотований тег на коміт, на якому пройшов набір: `git tag -a m1-2026-11-20 -m "М1: ..."`. У повідомленні тегу — коротко, які задачі пройшли. Тег пушиться разом із наступним дозволеним пушем.

### Заборонено

- `git push --force` і будь-яке переписування вже запушеної історії: `rebase`, `commit --amend`, `reset` для запушених комітів.
- **`git clean -x` і `git clean -X`.** Вони видаляють ігноровані файли, тобто `data`, `models`, `materials`, журнали й нотатки. Це знищить роботу користувача. `git clean` без цих ключів — лише після `git clean -n` і перегляду списку.
- `git reset --hard` і `git checkout -- .` за наявності незакомічених змін, яких ти не робив у поточному сеансі.
- Видалення гілки з незлитими змінами без запису причини.
- Масова зміна закінчень рядків чи форматування всього проєкту. Попередження Git про LF/CRLF нормальні, їх не виправляти окремим комітом.
- Зміна налаштувань git користувача (`git config --global`).

### Якщо закомічено зайве

- **Ще не запушено:** прибери файл із коміту (`git rm --cached`, потім `git commit --amend` для останнього коміту) і додай шлях у `.gitignore`.
- **Уже запушено, без секретів і особистих даних:** видали файл звичайним новим комітом.
- **Уже запушено ключ, токен чи особисті дані:** негайно повідом користувача. Ключ треба відкликати й замінити у провайдера: видалення з історії не скасовує витоку. Переписувати історію на GitHub — лише за прямою згодою користувача. Його змінюють, коли змінюється правило.
