# SA-116 — Source artifact lifecycle

write_action validates all paths before mutation and rejects input/consumed paths and duplicate destinations. Changed own source invalidates old/current/downstream metadata once, before any new registration. File writes and artifact registrations use one SQLite transaction; ordinary exceptions restore previous source bytes and roll back metadata. The regression is reproduced against the frozen old implementation: changing a later checker left only that checker active; the corrected implementation retains every current source. This is process-exception compensation, not a filesystem/database power-loss atomicity guarantee. Unreferenced immutable snapshots may remain after a low-level failure; they do not become accepted metadata.

POST /api/projects/{pid}/steps/{sid}/reconcile-source-artifacts is an idle-only authenticated metadata operation. It requires current approved plan/revision, done code step with positive assessment, matching successful saved run and completed checkers, written checkpoint source matching snapshot, and artifact v1 output hashes matching snapshot plus current published workspace bytes. The same source path may be owned by a later step in workspace, so source is restored from the original run, never by overwriting current workspace files. New immutable source snapshots carry run/path/hash/source-role provenance; old snapshots remain historical. Repeat calls are idempotent. No runtime, model call, step status, attempt counter or student bytes are changed.

Tests cover Python/JavaScript/C helper lifecycle, later-checker invalidation, storage-failure rollback, downstream invalidation, idempotent recovery and source/output/run/revision/assessment/checker tamper.
