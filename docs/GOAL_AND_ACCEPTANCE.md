# Мета й приймання StudyAssistant

Чинний нормативний документ від 13.11.2026. Замінює [ACCEPTANCE](ACCEPTANCE.md), [FIRST_LAB_ACCEPTANCE](FIRST_LAB_ACCEPTANCE.md) і [GENERALIZATION_ACCEPTANCE](GENERALIZATION_ACCEPTANCE.md), які лишаються історичними довідками. Підстава для змін — [оцінка інструкцій](audits/root-cause-2026-11-13/INSTRUCTIONS_REVIEW.md).

## Мета

StudyAssistant — універсальна локальна платформа для лабораторних робіт із комп’ютерних наук. Користувач дає умову, методичку, варіант і вхідні файли. Платформа:

1. витягує вимоги й питає лише про те, чого справді бракує;
2. пропонує план і чекає погодження;
3. генерує та ремонтує код, виконує його в ізоляції;
4. перевіряє фактичні результати;
5. готує звіт DOCX/PDF і матеріали до захисту;
6. чесно передає людині дії, які не може виконати сама (спеціальне ПЗ, фізичні вимірювання, зовнішні сервіси), з готовими файлами та інструкцією.

Логіка конкретної роботи береться з її джерел. Програма не містить правил під конкретний предмет, набір даних чи бібліотеку.

Чотири лабораторні жовтня (комп’ютерний зір, IoT, графіка, ШІ) — історичні приклади розроблення. Вони не є ціллю й не є мірою готовності. Їх повне виконання залежить від ручних дій користувача та ресурсів комп’ютера.

## Що означає «універсальна»

Універсальність визначає тип роботи, а не назва предмета. Набір перевірок має покривати такі осі.

| Вісь | Значення, які треба покрити |
|---|---|
| Вхід | коротка самодостатня умова; методичка PDF/DOCX із варіантами; кілька документів; скан або таблиця; стартовий код чи архів; файл даних |
| Стан умови | повна; з відсутнім параметром (потрібне уточнення); із суперечністю між джерелами |
| Виконання | Python; ще щонайменше дві мови з підтримуваних; SQL; робота з файлом даних; багатокрокова передача файлів між кроками |
| Перевірка | точний перерахунок оракулом; інваріанти й контрприклади; порівняння файлів чи зображень |
| Результат | звіт із таблицями; звіт із графіком або схемою; матеріали захисту |
| Межі | ручний крок із передачею пакета; відмова з поясненням, коли завдання поза можливостями; зупинка за ресурсами |
| Стійкість | ремонт після помилки виконання; продовження після перезапуску; зміна вхідних даних без повторення успішних кроків |

Одна задача зазвичай покриває кілька значень. Предметні сімейства зі старої матриці G01–G12 корисні як джерело різноманітних задач, але не як критерій.

## Головна метрика

**Частка задач наскрізного набору, що пройшли кожен етап:** план → погодження → виконання → перевірка оракулом → звіт → захист. Набір запускається в робочому шляху з реальною моделлю після кожної суттєвої зміни загального механізму.

Задача пройшла повністю, якщо:

- усі кроки виконала програма, без правок коду, чисел, плану чи станів БД з боку розробника під час запуску;
- зовнішній оракул підтвердив фактичні результати, а навмисно зіпсований результат він відхиляє;
- звіт і матеріали захисту створено, відкрито й переглянуто: у них немає вигаданих чисел, є потрібні розділи та правильні реквізити;
- для ручного кроку — пакет передачі повний, і програма зупинилася, а не видала вигадане свідчення.

Тестовий оператор може погоджувати план без редагування. Це не вважається втручанням.

## Рівні готовності

| Рівень | Умова | Які задачі зараховуються |
|---|---|---|
| **М0. Вимірювання** | Є набір із щонайменше п’яти малих задач різних типів з оракулами. Виміряно базовий прохід: для кожної задачі відомо, де вона зупинилася і чому | будь-які |
| **М1. Наскрізний прохід** | Щонайменше три задачі набору з трьох різних типів і двох мов проходять повністю на одній версії програми | задачі розроблення зараховуються |
| **М2. Широта й стабільність** | Щонайменше вісім із десяти задач проходять повністю у двох послідовних проходах. Покрито кожну вісь таблиці вище хоча б одним значенням, серед задач є одна з ручним кроком, одна з неповною умовою та одна не на Python | задачі розроблення зараховуються |
| **М3. Незалежне підтвердження** | Версію зафіксовано. Три нові задачі, яких не бачили під час розроблення, запускаються без змін програми; щонайменше дві проходять повністю. Усі критичні правила перевірено | лише нові задачі; якщо задача спричинила зміну програми, для М3 потрібна інша |

Критичні правила для М3: погодження плану перед виконанням, облік і ліміти бюджету, ізоляція виконання, збереження стану після перезапуску, чесна зупинка, відсутність вигаданих свідчень.

Поточний рівень на 13.11.2026 — жодного. М0 не досягнуто: набору немає.

## Що не є прийманням

- Зелені модульні тести. Вони перевіряють переходи між станами, а не результат роботи.
- Статус `completed` у БД.
- Позитивний вердикт модельного рецензента. Так само негативний вердикт моделі не є доказом дефекту: детермінована перевірка й оракул мають пріоритет.
- Запуск у копії з керованими відповідями моделі.

## Правила для задач набору

- Кожна задача має джерело умови, вхідні файли й оракул, який не бачить згенерованого коду. Оракул зберігається окремо й не передається моделі.
- У брифі немає готового розв’язку чи майбутніх чисел.
- За чинним правилом користувача від 22.10 новий тест має докладний бриф за [промптом](TASK_BRIEF_PROMPT_UK.md). За рішенням користувача від 13.11 дві з п’яти задач набору запускаються на «сирому» вводі, як це робитиме звичайний користувач, щоб виміряти саме планувальник.
- Невдалий прохід зберігається як є. Після виправлення механізму задача лишається в наборі й запускається знову.
- Задачі з важким навчанням моделей, які не вміщуються в ресурси ноутбука, у набір не входять. Для них перевіряється чесна зупинка за ресурсами.

## Історичний облік

Стан старих сценаріїв і чотирьох лабораторних збережено у трьох замінених документах та [реєстрі проєктів](handoff/PROJECT_REGISTER_2026-11-11.md). За старим протоколом прийнято 0 із 4 лабораторних і 0 benchmark. Ці числа більше не є головним показником і не повторюються в записах стану.
